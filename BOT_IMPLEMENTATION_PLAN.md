# План реализации Telegram бота психологического словаря

## Цель

Создать Telegram бота на Python, aiogram 3 и SQLite, который работает через webhook и ищет статьи словаря по следующему неизменному конвейеру:

1. нормализация пользовательского ввода;
2. точное совпадение;
3. при отсутствии точного совпадения — SQLite FTS5 с trigram tokenizer;
4. при пустом результате FTS5 — RapidFuzz по полному списку терминов и три кнопки «Возможно, вы имели в виду…»;
5. по нажатию на кнопку бот выдаёт определение выбранного термина.

Этапы ниже выполняются строго последовательно. Следующий этап начинается только после реализации текущего этапа и успешного прохождения его тестов.

## Принятые технические решения

- Python 3.12 или новее в виртуальном окружении, которым управляет Poetry.
- Poetry является единственным менеджером зависимостей: зависимости описаны в `pyproject.toml`, точные версии фиксируются в `poetry.lock`.
- aiogram 3.31.x с официальной интеграцией webhook через `aiohttp` и `SimpleRequestHandler`.
- SQLite через стандартный модуль `sqlite3`; обращения из асинхронных обработчиков изолируются в репозитории и выполняются без блокировки event loop.
- FTS5-таблица с `tokenize='trigram'` и внешним содержимым, синхронизируемая с основной таблицей триггерами `INSERT`, `UPDATE`, `DELETE`.
- RapidFuzz `process.extract(..., scorer=fuzz.WRatio, limit=3)` применяется только после пустого ответа FTS5.
- Callback-кнопки содержат числовой ID статьи, а не текст термина: `term:<id>`. Это укладывается в лимит Telegram и не зависит от длины или символов термина.
- База данных создаётся из `psychological_dictionary.json`. Исходный JSON во время работы бота не читается.
- Публичный URL и несекретные настройки поступают из переменных окружения; токен бота и webhook secret локально могут поступать из окружения, а в production читаются из файлов Docker secrets.
- Production-образ собирается многостадийным `Dockerfile`; Poetry создаёт проектное `.venv` на build-стадии, а runtime-стадия запускается без компиляторов и от непривилегированного пользователя.
- Основной production-стек запускается через `docker-compose.yaml`: один экземпляр бота за существующим host Nginx, именованный volume для SQLite и Docker secrets. Опциональный `docker-compose.caddy.yaml` добавляет Caddy для серверов без готового reverse proxy.
- Из-за SQLite сервис бота не масштабируется горизонтально несколькими репликами, использующими один файл БД.

## Этап 1. Каркас проекта и воспроизводимое окружение

### Реализация

- Создать пакет `app`, каталоги тестов и Poetry-проект в `pyproject.toml`.
- Настроить локальное проектное окружение командой `poetry config virtualenvs.in-project true`, чтобы оно создавалось в `.venv`.
- Зафиксировать основные зависимости: aiogram, aiohttp и RapidFuzz; pytest, pytest-asyncio и инструменты качества вынести в dev-группу.
- Создать и закоммитить `poetry.lock`; все установки выполнять через `poetry sync` без ручного `pip install`.
- Добавить Poetry-команды запуска приложения, импорта словаря и тестов.
- Настроить временную SQLite-базу для тестов.
- Добавить `.gitignore` для `.env`, рабочей БД, кэшей и виртуального окружения.

### Условия готовности

- Проект устанавливается в чистое виртуальное окружение командой `poetry sync`.
- `poetry check --lock` подтверждает согласованность `pyproject.toml` и `poetry.lock`.
- `poetry run python -m app.main --help` завершается без ошибки и не требует настоящего Telegram-токена.
- `poetry run pytest` на пустом каркасе запускается и завершается успешно.
- Импорт любого модуля приложения не создаёт БД, сетевых соединений или иных побочных эффектов.

### Юнит-тесты

- Smoke-тест импорта всех пакетов.
- Тест доступности CLI-команд без запуска сервера.
- Тест, что временный каталог данных подменяется через конфигурацию тестов.
- Тест, что версия Python соответствует ограничению проекта и обязательные runtime-зависимости импортируются из Poetry-окружения.

## Этап 7. FTS5 substring/trigram поиск

### Реализация

- Создать безопасный builder FTS5-выражения, экранирующий кавычки и служебный синтаксис `MATCH`.
- Выполнять trigram-поиск после неуспешного точного поиска.
- Отдельно учитывать совпадения в `search_blob`/термине и совпадения в тексте определения; совпадения термина ранжировать выше.
- Ограничить количество результатов и добавить детерминированную сортировку при равном ранге.
- Для запроса короче трёх символов не вызывать trigram-поиск, поскольку он не образует триграмму; сразу переходить к fuzzy fallback.

### Условия готовности

- Подстрока длиной от трёх символов находит ожидаемый термин внутри более длинного термина.
- Поиск поддерживает несколько слов после нормализации.
- Специальные символы FTS не вызывают синтаксическую ошибку и не изменяют смысл SQL.
- Результаты ограничены конфигурацией и стабильно упорядочены.
- Пустой результат представлен пустым списком.

### Юнит-тесты

- Подстрока в начале, середине и конце термина.
- Разный регистр и `ё/е`.
- Запрос из двух слов.
- Строки с кавычками, `*`, `OR`, `NOT`, скобками и дефисами.
- Запрос длиной 1–2 символа не обращается к FTS-репозиторию.
- Ранжирование совпадения в термине выше совпадения только в определении.
- Ограничение количества и детерминированный порядок.

## Этап 8. RapidFuzz fallback

### Реализация

- Загружать нормализованный список терминов и алиасов из репозитория в неизменяемый in-memory индекс при старте приложения.
- Реализовать `FuzzyMatcher`, использующий `process.extract`, `fuzz.WRatio` и `limit=3`.
- Дедуплицировать результаты по ID основной статьи, даже если одновременно совпали термин и его алиас.
- При равных оценках сортировать по score, затем по термину и ID.
- Возвращать оценку только для диагностики; пользователю показывать человекочитаемый термин без процента.

### Условия готовности

- Опечатка в одной или нескольких буквах возвращает релевантный термин первым.
- Возвращается не более трёх разных статей.
- Fuzzy matcher не обращается к SQLite на каждое сообщение.
- Основной термин и его алиас не создают дублирующиеся кнопки.
- Пустой словарь обрабатывается без исключения.

### Юнит-тесты

- Замена, пропуск, вставка и перестановка букв в русском термине.
- Опечатка с `ё/е` и разным регистром.
- Ровно три результата при наличии достаточного количества терминов.
- Словарь из одной и двух статей.
- Дедупликация основного термина и алиаса.
- Пустой choices и детерминированность одинаковых score.

- Подключить `SimpleRequestHandler` с проверкой `X-Telegram-Bot-Api-Secret-Token`.
- Использовать `handle_in_background=True`, чтобы быстро подтверждать webhook-запросы.
- На startup: проверить SQLite, применить миграции, открыть репозиторий, прогреть fuzzy-индекс и вызвать `set_webhook` с `secret_token` и ограниченным `allowed_updates` (`message`, `callback_query`).
- Не удалять webhook при обычном shutdown, чтобы остановка одного экземпляра не ломала другой при rolling deployment. Для удаления предусмотреть отдельную административную CLI-команду.
- Добавить `/healthz` для liveness и `/readyz` для проверки готовности БД и поискового индекса.
- Приложение слушает HTTP, опубликованный только на loopback хоста для Nginx; в опциональном варианте TLS завершается сервисом Caddy.

### Условия готовности

- Webhook route зарегистрирован только по настроенному пути.
- Запрос без корректного secret token отклоняется.
- Startup вызывает `set_webhook` с точным HTTPS URL, secret и разрешёнными типами update.
- До окончания инициализации readiness не возвращает успех; после инициализации возвращает `200`.
- Shutdown закрывает HTTP/Telegram/SQLite-ресурсы, но не вызывает `delete_webhook`.

### Юнит-тесты

- Фабрика приложения и регистрация маршрутов.
- Сборка webhook URL без двойных или пропущенных `/`.
- Startup hook с замоканным Bot API.
- Проверка аргументов `set_webhook`.
- Отсутствующий и неверный secret token.
- Состояния `/healthz` и `/readyz` до и после startup.
- Shutdown закрывает ресурсы и не удаляет webhook.

## Этап 12. Docker-образ и production Docker Compose

### Реализация

- Создать многостадийный `Dockerfile`: build-стадия устанавливает Poetry, проверяет lock-файл и создаёт `.venv`; runtime-стадия получает только приложение и готовое окружение.
- Зафиксировать digest или точный поддерживаемый тег базового Python-образа.
- Запускать контейнер от непривилегированного пользователя, включить unbuffered-логи, запретить запись в root filesystem и выделить `tmpfs` для временных файлов.
- Создать `.dockerignore`, исключающий `.git`, `.venv`, `.env`, `secrets`, кэши, локальную БД, исходные DOC/TXT и тестовые артефакты. В образ включать только нужный JSON либо уже подготовленную БД согласно выбранному процессу релиза.
- Создать основной `docker-compose.yaml` с `bot` и importer, рассчитанный на существующий Nginx хоста; Caddy вынести в опциональный `docker-compose.caddy.yaml`.
- Порт бота публиковать только как `127.0.0.1:8080` для host Nginx. В Caddy-варианте выдавать наружу только `80/443`.
- Подключить именованный volume к каталогу данных бота, где лежат SQLite-файл, `-wal` и `-shm`; отдельные volumes для сертификатов добавлять только Caddy override-файлом.
- Передавать bot token и webhook secret через Compose secrets, смонтированные только в сервис `bot`. Не помещать секреты в image, `.env` или YAML.
- Добавить healthcheck сервиса бота по `/readyz`, а в Caddy override — healthcheck Caddy; настроить `restart: unless-stopped`, лимиты ротации логов и корректный `stop_grace_period`.
- Зафиксировать один экземпляр `bot`; не использовать общий SQLite volume между несколькими репликами.
- Добавить одноразовый Compose profile/service для миграции и импорта словаря, использующий тот же image и data volume.
- Добавить документированные команды `docker compose build`, `up -d`, `ps`, `logs`, обновления, резервного копирования и восстановления SQLite.

### Условия готовности

- `docker compose -f docker-compose.yaml config --quiet` проходит без ошибок и без подстановки секретных значений в итоговую конфигурацию.
- Образ собирается только из `pyproject.toml` и `poetry.lock`; изменение зависимостей без обновления lock-файла ломает build.
- Runtime-контейнер запускается не от root, содержит рабочее `.venv` и не содержит Poetry cache, компиляторов, `.env` или файлов secrets.
- Внутри контейнера успешно проходит startup-probe SQLite FTS5 trigram.
- После пересоздания контейнера SQLite-база остаётся в named volume и содержит прежние статьи.
- В основном варианте aiohttp опубликован только на `127.0.0.1`; снаружи он недоступен. В Caddy-варианте наружу доступны только `80/443`.
- При отсутствии Docker secret сервис бота завершается до регистрации webhook с понятной ошибкой.
- После запуска bot переходит в состояние healthy, а HTTPS-запрос проходит через существующий Nginx; для Caddy override отдельно проверяется Caddy.

### Юнит-тесты

- Конфигурация корректно читает файлы из `/run/secrets`-подобной временной директории.
- CLI миграции/импорта использует путь к БД из mounted data directory.
- Healthcheck endpoint не зависит от внешнего Telegram API.
- Graceful shutdown завершает незаконченные обращения к репозиторию и закрывает SQLite-соединения.

### Контейнерные и конфигурационные тесты этапа

- `poetry check --lock` и сборка Docker image без сетевых действий на runtime-стадии.
- `docker compose config --quiet`.
- Проверка пользователя контейнера через `id`.
- Проверка отсутствия секретов и исключённых файлов в слоях/runtime filesystem.
- Запуск Compose с тестовыми secrets, ожидание healthy и запрос `/healthz`/`/readyz`.
- Пересоздание `bot` с проверкой сохранности SQLite volume.
- Остановка через `docker compose stop` с проверкой штатного завершения в пределах `stop_grace_period`.

## Риски, которые проверяем в начале реализации

- Серверный Python может быть собран с SQLite без FTS5 или без trigram tokenizer. Это блокируется startup-probe на этапе 2.
- Выбранный минимальный Python Docker image может содержать SQLite без trigram tokenizer. Это проверяется во время build/smoke-теста и повторно на startup.
- Trigram-поиск не работает содержательно для запросов короче трёх символов. Такие запросы после exact lookup направляются сразу в RapidFuzz.
- SQLite является синхронным. Репозиторий не должен блокировать event loop при долгих операциях; это проверяется архитектурно и нагрузочным smoke-тестом.
- Один SQLite-файл нельзя безопасно использовать как общую БД нескольких реплик на сетевом volume. Production Compose фиксирует одну реплику бота и локальный named volume.
- Резервное копирование работающей WAL-базы простым копированием одного `.db`-файла может быть неконсистентным. Процедура backup использует SQLite backup API либо согласованный checkpoint/остановку.
- Определения могут превышать лимит одного сообщения Telegram. Отправка делится на безопасные фрагменты.
- JSON содержит OCR-артефакты. Бот показывает сохранённый текст без автоматического смыслового исправления; `quality_flags` остаются доступны для последующей редакторской работы.
